# Dashboard

## Purpose

The Streamlit layer is meant to behave like a lightweight analytical product surface, not only like a demo UI.

It exists to consume the same artifacts generated by the canonical pipeline and expose them in business-facing workflows:

- executive overview
- portfolio risk exploration
- prioritization list
- simple retention impact simulation
- customer-level inference

## Canonical Data Source

The dashboard consumes outputs generated by the canonical pipeline path:

`src.cli.pipeline -> reporting artifacts + gold artifacts -> Streamlit pages`

Primary artifacts used:

- `artifacts/reports/executive_report.json`
- `data/gold/kpi_summary.csv`
- `data/gold/customer_prioritization.csv`
- `artifacts/models/enterprise_churn_bundle.joblib`

## Fallback Behavior

If the canonical reporting artifacts are missing, the dashboard can generate fallback outputs through `src.pipelines.dashboard_data`.

This behavior exists to keep the UI runnable in local portfolio scenarios, but it is explicitly surfaced in the interface.

Important:

- fallback mode is not the preferred operating state
- reviewers should treat canonical pipeline artifacts as the intended path
- the UI now shows when fallback artifacts are being used

Fallback mode is intentionally visible because hiding it would weaken technical credibility. A reviewer should be able to distinguish between canonical artifacts and locally generated emergency outputs without reading the source code.

## Runtime Components

- `apps/streamlit_app.py`: home page and customer-level inference view
- `apps/dashboard_ui.py`: shared layout shell, visual language, and reusable UI helpers
- `apps/dashboard_runtime.py`: shared dashboard asset loading and helper logic
- `apps/pages/executive_overview.py`: executive KPI page
- `apps/pages/risk_and_growth.py`: portfolio risk distribution and growth page
- `apps/pages/prioritization.py`: prioritized customer list
- `apps/pages/simulation.py`: retention impact simulation
- `pages/`: compatibility wrappers for Streamlit multipage discovery

## Layout Model

The main Streamlit surface is intentionally structured as:

- hero and operational status
- sidebar with runtime readiness and navigation context
- top-level cohort filters
- tabbed work area for overview, exploration, and scoring
- dedicated multipage views for executive, prioritization, and simulation workflows

This keeps the dashboard closer to a real analytical product and farther from a generic notebook wrapper.

## Design Intent

The dashboard should communicate:

- operational status
- artifact readiness
- whether the data is canonical or fallback
- business relevance, not just model internals

The goal is a credible analytical consumption layer, not a decorative ML demo.

## Review Standard

Changes to the dashboard should improve at least one of these dimensions:

- clarity of business interpretation
- visibility of artifact readiness
- consistency with canonical pipeline outputs
- resilience when artifacts are missing
- maintainability of shared runtime logic

Avoid changes that only add visual noise, duplicate pipeline logic in the UI, or hide degraded operating states.
